## ADR-162: Antigravity CLI provider

- **Date:** 2026-11-23
- **Decided by:** Anirudh Topiwala (contributor) + Claude Code, in a contributor session; for maintainer review in the PR.
- **Context:** Gemini CLI stopped serving Google AI Pro, Google AI Ultra and free-tier personal accounts on 2026-06-18 ("This client is no longer supported for Gemini Code Assist for individuals… migrate to the Antigravity suite"); those plans now run only through Antigravity CLI (`agy`). Gemini CLI still works with a paid API key, so the `gemini-cli` provider stays, but a personal Google plan can no longer back an autonomOS agent at all. `agy` is a separate CLI with its own hooks, config files, flags and conversation store, so it needs its own provider rather than a Gemini variant.
- **Decision:** Add an `antigravity` provider (binary `agy`), modeled on `gemini-cli`, with these choices, each measured on agy 1.5.14:
  1. **Hooks and MCP live in agy's global config.** agy reads hooks only from `~/.gemini/config/hooks.json`, a workspace's `.agents/hooks.json`, or a plugin, never from `--settings`, and has no documented way to point a process at another config file. So the server merges ONE named entry, `autonomos`, into `~/.gemini/config/hooks.json` and `mcp_config.json` at boot (after both planes are bound, like `writeGeminiSettings`), leaving every other entry as it was. A file that isn't a JSON object is left alone and the error logged. Every command is gated on `AUTONOMOS_SESSION_ID`, so the entries do nothing in the operator's own agy sessions. The MCP entry is `sh -c '[ -n "$AUTONOMOS_SESSION_ID" ] || exit 0; exec node "$0"' <script>`, so no node process starts there; a failing MCP server doesn't break an agy session anyway (measured).
  2. **Live status from 6 hook events.** SessionStart, PreInvocation, PreToolUse, PostToolUse, PostInvocation and Stop arrive as camelCase JSON (`hookEventName`, `toolCall.{name,args}`, `conversationId`). PreInvocation fires before every model call of a turn, so only `invocationNum` 0 maps to UserPromptSubmit; PostInvocation is dropped; a PostToolUse with a non-empty `error` is a PostToolUseFailure. agy has no permission-prompt or notification event (measured: registering `Notification` and waiting at the interactive "Run this command?" / "Allow calling this tool?" prompt fires nothing after PreToolUse), so "needs input" isn't observable (`analytics.supportFor`) and an agent waiting for approval shows as running that tool. Every hook command except SessionStart's MUST print nothing: agy reads each hook's stdout, and a PreToolUse reply of `{}` DENIES the tool ("tool call denied by pre-tool hook", measured); the relay discards curl's output, and a test pins that.
  3. **System prompt through the SessionStart reply.** agy reads a hook's stdout; SessionStart may return `{"injectSteps":[{"systemMessage":{"systemMessage":"…"}}]}`, and the agent answers from it (measured). The SessionStart command keeps curl's output, and the hook route answers with the prompt buildArgs stashed for that session (new optional `AgentProvider.hookReply`). Unknown session or relay down → `{}`. This replaces Gemini's prepend-to-the-first-prompt workaround (new `systemPrompt.method: "session-start-hook"`).
  4. **Conversation id from hooks, resumed with `--conversation`.** agy assigns the id; every hook carries it. The hook route persists it as `providerThreadId` (new optional `AgentProvider.threadIdFromEvent`; the Codex thread sink and the route now share `persistProviderThreadId`). `--conversation <unknown id>` silently starts a NEW conversation (measured), so `hasResumableThread` checks `~/.gemini/antigravity-cli/conversations/<id>.db` first: false only when the directory exists and the file doesn't, throws (fail open) when it can't tell.
  5. **Permissions and trust through `--settings`.** Two axes in agy's own vocabulary: `agentMode` (default | accept-edits | auto | plan; the settings value for `default` is `""`) and `toolPermission` (request-review | strict | proceed-in-sandbox | always-proceed). Both go in a session-only `--settings` JSON, never `--mode`: `--settings` rejects an unknown value at startup, while `--mode` silently ignores one (`--mode bogus` and `--mode default` both ran as auto). `agentMode` is always explicit, because with nothing set a personal account starts in `auto`. The default is `agentMode=default toolPermission=request-review`; legacy `bypass` maps to `toolPermission=always-proceed`, never to `--dangerously-skip-permissions`. Both `always-proceed` and `proceed-in-sandbox` count as never-asks, so widening a runtime default to either needs `confirmNeverAsks` (ADR-138). With Auto-Trust on, `trustedWorkspaces: [cwd]` in the same JSON skips the "Do you trust the contents of this project?" dialog without writing agy's settings file (measured); with it off, a startup notice explains the wait.
  6. **No paid AI credits.** The same `--settings` sets `useG1Credits: false`: when a plan's quota runs out, an autonomOS agent waits for it to refresh instead of spending purchased credits, whatever the operator's own agy setting. agy saves that key with `omitempty`, so false can't be pinned in its settings file; per-spawn is the only reliable place.
  7. **Drift probe: `settings-load`.** `agy --settings '{"k":"v"}' mcp list` validates the settings and exits with no session or model call; an unknown value fails with `unrecognized value`. agy never lists the allowed values, so this probe finds a removed value but never a new one.
  8. **Inbound messaging is `manual-queue`**, as for Gemini: the interactive TUI has no live inbound path.
- **Rationale:** Every choice follows a measurement on the real CLI rather than its docs, which were wrong or silent in places (docs list `--mode` values but not that bad ones are ignored; the "not signed in" banner prints on every healthy start while the saved login loads, so it is deliberately NOT a startup notice). Owning one named entry in agy's global files is the least invasive option agy allows; gating every command on the session id keeps the operator's own agy sessions untouched. `--settings` is the only per-process surface agy validates, so it carries everything per-agent.
- **Alternatives considered:** (a) Workspace `.agents/hooks.json` in the agent's cwd: writes into the operator's repository, and every repo an agent opens. (b) An agy plugin (`agy plugin install`): still global, adds a manifest format and an install step to manage, and gives nothing the named entry doesn't. (c) Relocating agy's config with the undocumented `ANTIGRAVITY_CONFIG_REL_DIR` / `ANTIGRAVITY_EXECUTABLE_DATA_DIR`: would also move the login, and undocumented knobs can vanish in any release. (d) `--mode` for permissions: silently ignores bad values. (e) `--dangerously-skip-permissions` for bypass: `toolPermission=always-proceed` is agy's own settings value and goes through the validated path. (f) Prepending the system prompt to the first prompt, like Gemini: loses it on a prompt-less spawn and is visible in the transcript as user text; agy offers a real injection point. (g) Driving agy over its ACP server (`agy acp`) for live inbound: a much bigger change to the PTY model; left for a follow-up.
- **Source:** Contributor session on 2026-11-22/23 (Claude Code), measuring agy 1.5.14 on a Debian 12 VM and macOS with personal Google accounts; then an end-to-end run of this branch on macOS: two Antigravity agents spawned through the REST API, live status (`tool_running` / `call_mcp_tool`), conversation id captured, channel server connected, `list_agents` and `send` called through MCP, the message queued for the second agent and delivered (receipt confirmed by the mapped UserPromptSubmit), and a restart resumed with `--conversation` and recalled the pre-restart message. The PR adding the provider.
